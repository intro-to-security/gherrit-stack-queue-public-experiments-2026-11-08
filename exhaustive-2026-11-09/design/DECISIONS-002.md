## What improved, and what remains necessary

The supported change removes an unnecessary requirement that a child's
associated base-OID fields equal the advanced named parent before this rebase.
In the actual public experiment, those fields still named the old parent.
Exact historical ranges and current named refs were already retained. A
separately authorized continuation kept the other identity, membership and ref
guards, rebased B successfully and retained that result before C returned a
conflict. Requiring that additional equality would have prevented this useful
action without protecting a fact it needed.

The replacement rule is action-specific: establish the identities, ranges,
ownership, target scope and guards that the particular operation needs. It does
not infer a missing historical range from a current parent. It also does not
turn a head guard into a target guard, a success response into a current result,
or a locally accepted result into settlement of an old remote request. These
obligations remain in the existing reconciliation core.

Candidate 002 also makes three mapping limits explicit. A rebase against an
exact captured target needs an adequate stability or guard argument before
dispatch. Preservation of a change needs a justified transformation or accepted
resolution, rather than literal patch equality. Reviewer comparisons must use
each submission's own base-to-tip range, including binary blob transitions,
rather than compare unrestricted tip trees.

The candidate's named-base-at-execution alternative describes proposed accepted
intent. It is **not a documented promise about the provider's exact
target-selection instant**. A concrete adapter must establish which moving
target scope the user accepts and which behavior the provider supports. A base
name or membership change is separate from ordinary movement of the same target
ref. If the effect applies outside the accepted scope, preserve the original
intent and actual outcome without accepting, rolling back or resending it.

## Comparison with the alternatives

The qualified strict pilot retains the strongest hosted-state promise, but no
sufficient handoff excluding old suffix writes was found. Its inability to
complete useful overlapping repetition is a real cost. Keeping that gate is a
provisional proposal boundary, not a claim that the user's goals require it.

The fixed-order exact-review alternative could permit repeated publication
under a weaker hosted-state promise. It admits temporary wrong hosted state,
delayed or missed observations and recurring author decisions. It still owes a
useful implemented repeated workflow and an argument bounding old operations'
effects and review lifecycle. Fixed order alone supplies neither.

Automatic restoration could reduce those decisions, but it needs more accepted
intent. The explicit-reset counterexample defeats a clean three-tree merge as
a sufficient rule. Path/value intent adds composition, rename, deletion, mode,
binary and validation work. The evidence does not show a lower total burden.

No candidate dominates across availability, hosted-state correctness, canonical
review continuity and human effort. No operating promise is selected here.
The shared identity, history, custody and reconciliation model remains useful
under each alternative. A CLI, hook or service cannot decide the promise for us.
