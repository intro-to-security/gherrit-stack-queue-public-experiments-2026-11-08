# Public source exploration

The additional public sources do not answer the remaining lifecycle question: whether a direct merge UUID becoming `merged` means that every automatic suffix head/base write has finished, or how a native suffix rewrite handles a client update that arrives later. The current public schema exposes no separate suffix operation, generation, completion result, or cancellation endpoint. This is a bounded source finding, not evidence that delayed writes occur or that the server lacks an internal compare-and-swap.

The search did uncover useful discriminators. First publication precedes stack membership by design; the `stacked` webhook reports membership but its existence alone does not establish an Actions trigger. Recent reports distinguish nearby-line approval loss from distant-line retention after direct API merges. Current CLI force pushes also carry a stack-specific push option, so plain Git pushes and the latest official CLI are different review-retention producers.

## Completion and arbitration

The full pinned public [OpenAPI description](https://github.com/github/rest-api-description/blob/2f8f80e47ea4d3292cf4e37ba9d9b25475e06140/descriptions/api.github.com/api.github.com.json) was downloaded successfully: 14,206,638 bytes, SHA256 `b8973e498305c0e45891c45a109901f9caf6ecbf8ad0e53404a7947c503e120f`. [openapi-focused.json](receipts/openapi-focused.json) retains every path containing `/stacks` or `merge-async` and their direct component references.

Those paths provide stack list/create/get/add/unstack and async merge submission/result. There is no stack-rebase or async-cancel path in that enumeration. The pending result has the selected PR's expected head, options and UUID; final results carry the merge SHA or a message, with no suffix-generation field. The result expires 24 hours after its latest update. These are schema facts; they do not reveal server scheduling or suffix-write preconditions.

Live public GraphQL introspection covered `PullRequestStack`, `PullRequestStackEntry`, `PullRequest`, the force-push and automatic-base-change events, queue admission/removal events, and all public `Mutation` fields. Stack fields describe membership, target and position. No dedicated stack rebase/cancel mutation or suffix-settlement field appeared. This observation covers the queried public schema at its retrieval time, not private website interfaces or future additions.

**The source audit identified a generic public rebase path.** `updatePullRequestBranch` accepts `pullRequestId`, optional `expectedHeadOid`, and `updateMethod` (`MERGE` or `REBASE`, default `MERGE`), plus a client identifier. Its payload returns the updated PR and client identifier, with no operation receipt. Three additional type receipts retain that input, payload and enum. The input describes `expectedHeadOid` as “The head ref oid for the upstream branch.” The official [`gh pr update-branch` caller](https://github.com/cli/cli/blob/736c68f674113337685e3eb1f908602a03b8f99b/pkg/cmd/pr/update-branch/update_branch.go) passes the selected PR's `HeadRefOid`, establishing the client expectation. Neither description promises a suffix-wide guard. The ordinary REST `update-branch` description explicitly guards the selected PR's HEAD but describes merge updates; its full path is retained separately in the OpenAPI receipt. A dedicated stack operation's absence does not prove that the generic GraphQL rebase rejects stacks or cannot cascade. That capability needs a fresh isolated probe or provider clarification; this read-only lane did not invoke it. The subsequent [workflow experiments](../workflow/RESULTS.md) accepted native-member REBASE and composed selected-member updates, with exact scope and completion limits.

The official [async API GA notice](https://github.blog/changelog/2026-10-01-github-async-merge-api-generally-available/) recommends submit-and-poll for programmatic merge. It adds no suffix or concurrent-writer semantics. The baseline's distinction between direct landing and final queue admission therefore stands.

The current official client makes the same distinction. In [`runMergeHeadless`](https://github.com/github/gh-stack/blob/bd0a32504f9ae9f795875a9e6bb90ff7408fda08/cmd/merge.go#L379), `IsMerged()` prints success and returns immediately; `IsEnqueued()` prints queue admission and returns. Its polling path checks the same statuses, with no suffix reads afterward. The [async client](https://github.com/github/gh-stack/blob/bd0a32504f9ae9f795875a9e6bb90ff7408fda08/internal/github/merge_async.go) and [unit tests](https://github.com/github/gh-stack/blob/bd0a32504f9ae9f795875a9e6bb90ff7408fda08/internal/github/merge_async_test.go) serialize requests and decode stubbed responses. This is client implementation evidence, not an implementation of the hosted native writer.

History adds no missing fence. The async wrapper has one path-history commit, [the merge command introduction](https://github.com/github/gh-stack/commit/68ce60c76096c1aecdc19a8af6fa7e89d31ebc2b). Its [PR review](https://github.com/github/gh-stack/pull/307) clarifies queue routing and explicit merge actions, not suffix arbitration. Several bot review claims about queue support were explicitly rejected by the collaborator; neither bot comments nor a historical draft are current API contracts.

It supplies no public receipt, operation ID, polling protocol, captured starting head set, cancellation contract, or concurrency precondition. The baseline current GitHub Docs guide already establishes the intended effect. Re-reading the effect cannot fill the missing completion boundary.

Live event schemas confirm that a force-push event can expose before/after commits, actor and ref; those fields are nullable. `createdAt` is object-creation time. Base-change success/failure events identify old/new base strings, not all suffix-head completion. Queue removal includes a reason. None exposes the async UUID. The [push webhook](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push) has before/after/ref/forced fields, while the same reference warns that `sender` may be the placeholder `ghost`. Positive marker transitions can discriminate real overwrites when attribution is established; missing events or quiet reads cannot establish settlement.

## First CI, rules and producer differences

There is an explicit published answer for the first-membership boundary. The current official [CLI webhook reference](https://github.com/github/gh-stack/blob/bd0a32504f9ae9f795875a9e6bb90ff7408fda08/docs/src/content/docs/reference/webhooks.md) says a PR is created before stack membership, so its `opened` event never contains a stack object; `stacked` reports the later addition. Collaborator `skarim` states this in [Discussion 140](https://github.com/github/gh-stack/discussions/140#discussioncomment-17472078) and [announces the webhook live](https://github.com/github/gh-stack/discussions/140#discussioncomment-17783595). This closes the metadata-availability question, not the workflow-dispatch question.

The current [Actions event guide](https://github.com/github/docs/blob/8cd1075179df75319912891d6620c9cb78eefb4d/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md#pull_request) defaults `pull_request` workflows to `opened`, `synchronize` and `reopened`; its referenced [activity-types list](https://github.com/github/docs/blob/8cd1075179df75319912891d6620c9cb78eefb4d/data/reusables/actions/workflow-triggers-pull-request-activity-types.md) does not list `stacked`. A live membership webhook is therefore insufficient evidence that `types: [stacked]` dispatches Actions. The guide also identifies `GITHUB_SHA` as the test-merge commit and distinguishes it from the PR head. Preserve both producer and SHA when testing a required check.

The [stack-specific CI guide](https://github.com/github/docs/blob/8cd1075179df75319912891d6620c9cb78eefb4d/content/pull-requests/how-tos/merge-and-close-pull-requests/optimizing-ci-for-stacked-pull-requests.md) promises trigger evaluation against the stack base for members. [Issue 425](https://github.com/github/gh-stack/issues/425) reports middle PRs missing their first trunk-filtered workflow because creation preceded stack registration; [Discussion 567](https://github.com/github/gh-stack/discussions/567) reports the bottom PR initially taking the standalone condition. They are user reports, consistent with the membership ordering but not proof that current dispatch always fails.

Other reports distinguish separate failure modes: [319](https://github.com/github/gh-stack/issues/319) reports stale/missing test-merge refs; collaborator `skarim` [acknowledged investigation](https://github.com/github/gh-stack/issues/319#issuecomment-5085253743) in July, without a current resolution in the fetched comments. [548](https://github.com/github/gh-stack/issues/548) reports stale/chained test-merge parents after rebase. Do not merge these mechanisms with the first-event ordering report merely because both can suppress CI.

Recent review evidence supplies a targeted case, not a universal defect. In [Discussion 313](https://github.com/github/gh-stack/discussions/313#discussioncomment-19448504), a November 6 report compares upper edits adjacent to a lower edit with edits far away in the same file. It reports approval dismissal for adjacent edits and retention for distant edits under stale-review/latest-push/CODEOWNERS rules, with unchanged tree/diff; an [organization-ruleset follow-up](https://github.com/github/gh-stack/discussions/313#discussioncomment-19449853) repeats that distinction. Its proposed diff-hunk explanation is a hypothesis. [Discussion 582](https://github.com/github/gh-stack/discussions/582) separately reports partial rebase-merge approval loss, including replies with stale-dismissal off and unattributed-change checks on. These reports justify a nearby-line control if review retention remains decision-relevant.

Client producer identity changed in [PR 562](https://github.com/github/gh-stack/pull/562), included in [v0.3.0](https://github.com/github/gh-stack/releases/tag/v0.3.0). Current [`gitops.go`](https://github.com/github/gh-stack/blob/bd0a32504f9ae9f795875a9e6bb90ff7408fda08/internal/git/gitops.go#L258) sends a command-local `push.pushOption=pull.stacked` for forced pushes and falls back only for the unsupported-options diagnostic. The PR says the signal supports review retention for tree-same diffs; the linked server changes are private and were not inspected. This proves the client signal, not server deployment or universal retention. Plain Git force pushes, this CLI producer, website rebase and post-merge native rebase should retain distinct identities in experiment results.

## Ordinary sync and source drift

Current [`sync`](https://github.com/github/gh-stack/blob/bd0a32504f9ae9f795875a9e6bb90ff7408fda08/cmd/sync.go) fetches/reconciles, refreshes PR state, advances the trunk, rebases, pushes active refs atomically by default, refreshes PRs, and can create/update the native stack. It is not a local-only control. A push failure currently warns and continues to later PR/catalog work; an exit code alone is insufficient evidence of the hosted branch result. [`init`](https://github.com/github/gh-stack/blob/bd0a32504f9ae9f795875a9e6bb90ff7408fda08/cmd/init.go) with explicit existing local branches records local catalog metadata and performs PR lookups; it has no remote-write call in its argument path. Missing local refs are created from predecessors, so remote-tracking refs must not be mistaken for adopted local histories.

Released fixes narrow client regressions: [586](https://github.com/github/gh-stack/pull/586) validates stale merged-PR cutoffs; [590](https://github.com/github/gh-stack/pull/590) follows automatic base retargets and blocks publishing before local repair; [596](https://github.com/github/gh-stack/pull/596) makes Git pushes atomic while explicitly excluding PR/API updates from that atomicity. None claims a fence against hosted writers. The v0.3.0 and current-main blobs for init, sync, utils and gitops were independently compared and match. The `syncStack` helper in `cmd/submit.go` preserves merged remote members and avoids an API write for an exact member-order match; read-failure, missing-stack and append paths can instead create/update native groups, so that no-op is conditional.

Publication time matters. The official [October 6 GA notice](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/) describes approval preservation, signed native replacement commits, bypass, queue grouping and staged auto-merge rollout. Some current `gh-stack` FAQ/UI prose still says native commits are unsigned or bypass/auto-merge unavailable. [Docs issue 46413](https://github.com/github/docs/issues/46413) has a later contributor confirmation that auto-merge is supported. These conflicts make an older CLI guide unsuitable as the sole authority for current hosted rollout. They do not resolve suffix lifecycle or arbitration.
