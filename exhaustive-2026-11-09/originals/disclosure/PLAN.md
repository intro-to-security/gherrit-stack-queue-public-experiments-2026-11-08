# Avenues and completion criteria

The aim is to exhaust the identified, accessible, relevant evidence avenues and follow newly discovered discriminating ones. There is no finite experiment that exhausts all future GitHub behavior. Every avenue must end with retained findings, a concrete capability/authority dependency, or a precise reason further repetition cannot distinguish the remaining hypotheses. Do not turn a missing premise into a passing test.

1. Primary documentation: guides, REST/OpenAPI, GraphQL schema and events, webhooks, CLI code/tests/history, official issue/discussion/support responses and release notes. Seek exact suffix completion/arbitration semantics; prepare a precise external clarification request if none is published.
2. Causal native-write experiments: instrument force-push/base-change events; validate event capture with positive controls; compare post-terminal marker publication, earlier in-flight publication, and ordinary post-merge sync. Cover distinct direct methods, same-order suffix lengths and failures where they discriminate. Preserve causal order and optional/missing evidence.
3. Website evidence: authenticated button initiation, observable request/result or UI feedback, PR/Git/event outcomes, interruption/recovery evidence and contrasts with API semantics. Verify available browser instrumentation before claiming capture.
4. Full staged workflow: A–B publication, local edits to A/B, old A landing, independent F-only publication/landing, canonical B amendment and repeated import. Check actual public source scope, archive/checkpoint preservation and old pending custody. Exercise refusal and inseparable/joint-review cases without silently substituting a different workflow.
5. Concrete recovery protocols: compare strict refusal and explicitly weaker retained-intent/detected-drift candidates under delayed effects, legitimate remote changes, partial/unknown outcomes, stale workers, transfer and rollback. Use actual Git and a bounded state explorer with challenged oracles. Injected effects test the client, not actual provider ordering.
6. Target profile: inspect actual GHerrit CI/rules and reproduce consequential first-publication, rewrite, method, producer/SHA and queue paths in synthetic fixtures. Reuse valid prior results; add controls only for new gaps or implementation differences. No production setting mutation.
7. Human workflow and reviewer evidence: execute mechanical walkthroughs and prepare concrete human tasks. Agent results do not establish human comprehension or preference. Seek user input only where actual human evidence or communication authority is indispensable, while completing independent work.
8. Acceptance and migration: corrected dispatch-boundary tests, custody/adoption/rollback rehearsals and feasible durability tests. Probe available disposable VM/runtime capabilities read-only before any power-loss experiment; do not disrupt the host or another chat's runtime.
9. Independent audit: review harness premise/oracle coverage, exact raw evidence, cleanup and every avenue disposition. Publish findings to #518 or child issues with current-source/evidence links, then reassess the design using the accumulated evidence. Preserve unresolved normative choices and unavailable checks explicitly.

## User-added source avenue

Inspect current and relevant released cli/cli core command routing and stack-related code as well as github/gh-stack; determine builtin/extension composition from source rather than assuming the locally installed binary is current. Search public third-party clients/examples that actually call native /stacks, merge-async or PullRequestStack APIs. Trace concrete guards, polling, suffix sync, failure handling and tests. Preserve source identities and exact call paths; client assumptions and mocks establish client behavior, not server ordering or forward-compatibility promises. Use counterexamples and new code findings to adapt experiments. Root owns this read-only supplement until an explicit new allocation.
