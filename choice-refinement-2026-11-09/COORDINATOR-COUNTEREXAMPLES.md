# Exposed coordinator witnesses

These are design arguments for later adversarial comparison, not executed results or reserved confirmation cases. They are withheld from the divergent architects during their proposals. A warm critic may inspect them; a fresh critic receives only deliverables, common contracts and neutral criteria.

## Late suffix writes after an order inversion

Test a proposed retained-inputs/detect-and-reconcile promise against irreversible review lifecycle, not just content backups.

Start with A–B–C. Old A lands, and a native operation may still produce same-order suffix B1→C1. The client safely parks and rebuilds the surviving canonical reviews in order C2→B2, then sets B's base to C's managed branch. If an old native effect can subsequently put B1 and C1 on those managed heads, B's base can now contain B1. GitHub's documented indirect-merge behavior can terminalize canonical B before its intended new-order landing. All authored inputs may be archived, yet reopening a merged review is unavailable. A general recovery claim must either exclude this interleaving under a supported contract, prevent it, or explicitly count the lost canonical-continuity promise and replacement-review cost.

This witness does not prove GitHub performs that delayed interleaving; current evidence does not establish such writes. It falsifies the logical claim that archiving inputs alone makes every possible concurrent native topology rewrite harmless. The premise is relevant only when a candidate intentionally admits that uncertainty rather than relying on a supported no-later-write contract.

## Order-preserving work is a separate proof obligation

Publishing a fresh follow-up F before surviving B, while preserving the relative order of existing B/C reviews, does not obviously produce that same inversion. Fresh F is outside an older suffix operation's known targets. This may support a narrower recoverable protocol or staged publication, but it is not a proved reduction: account for actual native scope, old/new base writes, unmentioned suffix work, content incorporation, required rules and completion reporting. Show useful repetition and explicit user costs. Do not promote the absence of the inversion witness into a full correctness proof.

## A default is not dominance

An explicit command may satisfy the first client without an outer-push ambiguity, while a compatible hook can still offer a convenience a user values. One publishing authority can be located in a checkout or service, but moving it changes collaboration, uptime and deployment costs. A history comment can index exact ranges while a richer view renders comparisons, yet discoverability and hosting costs still vary. A shared semantic core can remove duplicate engines without establishing that one interface/deployment universally dominates another.

For each proposed closure identify whether an independent implementation decision disappears, one choice becomes a conditional default, a requirement remains unmet, or a real benefit has simply been deferred. The new task asks for actual reductions; do not count renamed axes as multiple solved questions.
